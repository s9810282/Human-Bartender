## 1. 레포 폴더 구조 — 파트당 폴더 하나

```
Human-Bartender/
├─ HumanBartender/     유니티 프로젝트        → 프로그래밍 파트
├─ ArtResources/       아트 원본 (이름별 폴더) → 아트 파트
└─ Document/           기획 파트 폴더          → 우리
   ├─ 데이터/           게임 데이터 파이프라인 (엑셀 3종 · json · 빌드 도구)
   ├─ 고현정/           개인 작업 폴더
   ├─ 이기현/           개인 작업 폴더
   ├─ 이준서/           개인 작업 폴더
   └─ 임수진/           개인 작업 폴더
```

- 기획은 **Document/ 밖을 건드리지 않습니다.** 유니티·아트 폴더는 보기만.
- 개인 폴더는 자기 것만 수정합니다. 남의 폴더는 열람 자유, 수정 금지.
- 웹 프로토타입 관련 파일은 이 레포에 넣지 않습니다 (별도 관리).

## 2. 데이터 파일 소유자 — 이 파일은 이 사람만 수정한다

| 파일 | 소유자 | 내용 |
| --- | --- | --- |
| `Document/데이터/LUNA_System.xlsx` | **고현정** | 1부 제조·운영 (칵테일 · 밸런스 · 랜덤 손님) |
| `Document/데이터/LUNA_Narrative.xlsx` | **이준서** | 대본 · 단골 · 퀘스트 · 연출 (최종본) |
| `Document/데이터/LUNA_Draft.xlsx` | **이기현** | 대사 초안 (원고지) |

왜 이렇게 하나요? — **엑셀은 git이 병합(merge)을 못 하는 파일**입니다. 두 사람이 같은 엑셀을 고치면 한쪽 작업이 통째로 사라집니다. "파일 1개 = 소유자 1명"이면 그 사고가 아예 안 생깁니다.

- 남의 파일은 급해도 직접 고치지 않습니다. 소유자에게 요청하세요 (노션 코멘트/카톡).
- **열어서 보는 것**은 자유입니다. 충돌은 수정에서만 생깁니다.
- 대사 흐름: 기현님이 Draft에 쓰고 상태=전달완료 → PD가 가져가 Narrative에 반영. **전달한 뒤의 수정 요청은 노션 코멘트로.**

## 3. 브랜치 — 기획은 전원 `plan` 브랜치에서 산다

기획 4명은 **공용 브랜치 `plan` 하나**에서 작업합니다. 클론 후 딱 한 번 갈아타면 끝:

```bash
git checkout plan        # 최초 1회 — 이후 브랜치를 바꿀 일 없음
```

- **개인 브랜치는 만들지 않습니다.** 엑셀이 병합 불가라, 같은 파일이 두 갈래로 갈라지면 합치는 날 한쪽이 통째로 사라집니다. plan 하나를 공유하고 "자주 pull, 자주 push"가 안전장치입니다.
- **develop에는 직접 커밋하지 않습니다.** develop은 프로그래밍 파트의 통합 공간 — 기획 데이터는 PD가 빌드 통과를 확인하고 **plan → develop 병합**으로 전달합니다 (금요 통합 빌드 정기 + 프로그래밍 요청 시 수시).
- 기획은 `Document/`만 만지고 프로그래밍은 그 밖을 만지므로 **plan↔develop 병합은 항상 무충돌**입니다.

## 4. 하루 작업 루틴

```
① 작업 시작 전:  git pull          ← 엑셀 열기 전에! (열고 나서 받으면 이미 늦음)
② 작업                              (내 위치는 항상 plan 브랜치 — 확인: git branch)
③ 작업 끝:       (데이터를 고쳤으면 빌드 확인) → git add → commit → push   ← 그날 안에
```

- 커밋 메시지는 한 줄: `날짜 이름 무엇을` (예: `0723 기현 d4 삼호 초안 12줄`)
- push를 다음 날로 미루면 다음 날 아침 pull 받은 사람과 어긋납니다. **그날 작업은 그날 올립니다.**

## 5. 데이터를 고쳤다면 — push 전 체크

```bash
python3 Document/데이터/tools/build.py     # ✅ 검증 통과 확인 후에만 push
```

1. 빌드 실패 상태로 push하면 **전원이 깨진 데이터를 받습니다.** 에러 메시지에 뭐가 틀렸는지 나오니 고치고 다시.
2. 빌드가 만든 `Document/데이터/json/` 변경분도 **같이 커밋**합니다 — json의 변경 내역이 곧 "무엇이 바뀌었나" 기록입니다.
3. `gen_luna_data.py`는 **절대 실행 금지** — 시트가 초기 데이터로 덮입니다. 빌드는 `build.py`만.

## 6. 충돌이 났을 때

**엑셀 충돌** (`Cannot merge binary files`):

git은 두 사람의 엑셀 수정을 합칠 수 없습니다. 한쪽을 통째로 버리는 선택만 가능합니다:

```bash
git checkout --theirs <파일>   # 서버(상대방) 것을 살리고 내 수정을 버림
git checkout --ours   <파일>   # 내 것을 살리고 상대방 수정을 버림
git add <파일> && git commit
```

→ §2 소유자 규칙을 지키면 **이 상황 자체가 생기지 않습니다.** 생겼다면 규칙이 깨진 것이니 PD에게 알려주세요.

**`json/` 충돌**: 고민하지 마세요. json은 엑셀에서 자동 생성되는 결과물입니다:

```bash
python3 Document/데이터/tools/build.py     # 최신 엑셀로 재생성하면 그게 정답
git add Document/데이터/json && git commit
```

**유니티 파일·아트 파일 충돌**: 기획이 판단하지 않습니다. 해당 파트에 알리고 기다리세요.

## 7. 금지 3가지

1. `git push --force` — 팀 히스토리가 지워집니다. 필요하다고 느껴지면 무조건 PD 먼저.
2. 100MB 넘는 파일 커밋 — GitHub이 거부합니다. 큰 파일은 PD와 상의.
3. 남의 소유 파일 수정 — §2.

## 8. 자주 묻는 것

- **Q. 엑셀을 열어놨는데 pull 받으라고 하네요?** → 엑셀을 먼저 닫고 pull, 그다음 다시 여세요. 열어둔 채 pull 받으면 저장할 때 남의 수정을 덮습니다.
- **Q. `~$LUNA_...xlsx` 같은 파일이 생겼어요** → 엑셀이 만드는 임시 파일입니다. 커밋되지 않게 설정돼 있으니 무시하세요.
- **Q. 실수로 뭔가 지웠어요** → 당황하지 말고 아무것도 더 하지 말고 PD 호출. git에는 히스토리가 있어서 대부분 복구됩니다.
