## 0. 시작하기 전에 — 3분 요약

L.U.N.A는 **사이버펑크 바텐더 게임**입니다. 손님 이야기를 듣고 칵테일을 만들어 주는 게임이죠.

그런데 게임 안에는 **"정해진 내용"이 아주 많습니다.**

- 진피즈는 재료가 뭐고 값이 얼마인지
- 포트 할아버지는 어떤 술을 좋아하는지
- 3일차에 손님이 몇 명 오는지
- 크리스가 튜토리얼에서 무슨 대사를 하는지

이런 걸 전부 **프로그램 코드 안에 적어두면** 큰일 납니다. 대사 한 줄 고치려고 프로그래머를 불러야 하고, 고칠 때마다 게임이 고장 날 수 있으니까요.

그래서 **"내용"과 "프로그램"을 분리**합니다.

```
[ 내용 ]  진피즈 = 진 1.5oz + 레몬 0.5oz + 설탕 1tsp, 220골드   ← 데이터 (기획자가 관리)
[ 프로그램 ]  칵테일을 만들고 점수를 매기는 규칙                  ← 코드 (프로그래머가 관리)
```

이 **"내용"을 담아두는 파일**이 바로 JSON입니다. 이 문서는 그 JSON들을 하나하나 설명합니다.

### JSON이 뭔가요?

**컴퓨터가 읽기 좋게 정리한 메모장**이라고 생각하면 됩니다. 규칙은 딱 두 가지예요.

**규칙 1 — `{ }` 는 "이름표가 붙은 묶음"** (사전, 프로필 같은 것)

```json
{
  "이름": "진피즈",
  "가격": 220,
  "도수": 8.0
}
```
→ "이름이 진피즈이고, 가격이 220이고, 도수가 8.0인 무언가"

**규칙 2 — `[ ]` 는 "줄줄이 나열한 목록"** (명단, 리스트 같은 것)

```json
["진", "레몬", "설탕"]
```
→ "진, 레몬, 설탕 이렇게 세 개짜리 목록"

이 둘을 섞으면 복잡한 것도 표현할 수 있습니다.

```json
[
  { "이름": "진토닉", "가격": 180 },
  { "이름": "진피즈", "가격": 220 }
]
```
→ "칵테일 두 개가 들어있는 목록. 각각은 이름과 가격을 가짐"

**이것만 알면 이 문서를 전부 읽을 수 있습니다.** 나머지는 다 응용이에요.

## 1. 데이터는 어디서 와서 어디로 가나요? (파이프라인)

가장 많이 하는 오해가 **"JSON 파일을 직접 고치면 되겠네?"** 인데, **아닙니다.**

```
① 데이터/LUNA_System.xlsx        ← 제조·운영 담당이 고칩니다 (칵테일·밸런스·랜덤 손님, 8시트)
   데이터/LUNA_Narrative.xlsx     ← 대사·서사 담당이 고칩니다 (대본·단골·취향·호감도·퀘스트·연출, 22시트)
        │                            ⚠ 한 파일 = 담당자 한 명. 남의 시트를 복사해 넣으면 빌드 에러
        ▼  python3 데이터/tools/build.py   (두 파일을 합쳐서 검증)
② 데이터/json/*.json             ← 자동으로 만들어집니다 (20개 + 대본)
        │                            ⚠ 직접 고치면 다음 빌드 때 사라집니다
        ▼  python3 데이터/tools/bundle_proto.py
③ junseo874.github.io/js/data.js ← 웹 프로토타입이 읽는 최종 파일
```

### 왜 이렇게 번거롭게 하나요?

| 단계 | 이유 |
| --- | --- |
| **엑셀에서 쓴다** | 기획자에게 가장 익숙한 도구입니다. 표로 보이니까 실수도 덜 하고요 |
| **build.py가 검사한다** | 오타·빠진 값·앞뒤 안 맞는 데이터를 **자동으로 잡아줍니다.** 검사에 걸리면 JSON을 아예 안 만들어요 (= 고장난 데이터가 게임에 못 들어감) |
| **JSON으로 내보낸다** | 게임 프로그램이 읽기 가장 빠르고 편한 형태입니다 |

> ### ⚠️ 가장 중요한 규칙
> **`데이터/json/` 안의 파일은 절대 손으로 고치지 마세요.**
> 그건 "결과물"입니다. 엑셀을 고치고 `build.py`를 다시 돌리세요.
> (프로그래머가 구조를 확인하려고 **읽는 건** 얼마든지 괜찮습니다.)

### 검사기(build.py)가 잡아주는 것들

빌드할 때 자동으로 이런 걸 검사합니다. 하나라도 걸리면 빌드가 실패해요.

- 없는 재료를 레시피에 썼는지 (오타 등)
- 한국어만 쓰고 영어 번역을 빠뜨렸는지
- 같은 ID를 두 번 썼는지 (복붙 실수)
- 조건식·효과식 문법이 틀렸는지
- 플래그 이름에 오타가 났는지
- 호감도를 아무리 잘 올려도 엔딩 조건에 도달 못 하는지 (밸런스 시뮬레이션)

## 2. 전체 파일 지도

`데이터/json/` 안에는 **20개 파일 + `script/` 폴더**가 있습니다.

### 왜 하나로 안 합치고 20개로 나눴나요?

기준은 딱 하나입니다.

> **"항상 같이 불러오고, 항상 같이 수정하고, 혼자 있으면 의미가 없는 것"만 한 파일로 묶는다.**

예를 들어 등급컷·팁 배율·호감도 표는 **밸런스를 맞출 때 항상 같이 만지니까** `balance.json` 하나로 묶었습니다.
반대로 칵테일과 캐릭터는 아무 상관이 없으니 따로 뒀고요. 이렇게 하면 필요한 것만 불러올 수 있고, 여러 명이 동시에 작업해도 충돌이 덜 납니다.

## 3. 모든 파일에 공통으로 적용되는 규칙 4가지

파일별 설명에 들어가기 전에, **전 파일에 공통으로 통하는 약속**을 먼저 알아야 합니다.

### 규칙 ① 사람이 읽는 글자는 반드시 한국어+영어 쌍

게임을 영어로도 낼 거라서, **사람 눈에 보이는 모든 글자**는 한국어와 영어를 같이 씁니다.

```json
"name": { "ko": "진피즈", "en": "Gin Fizz" }
```

- `ko` = 한국어, `en` = 영어
- **하나라도 비어 있으면 빌드가 실패합니다.** 나중에 몰아서 번역하려다 빠뜨리는 사고를 막기 위해서예요.
- 반대로 **사람이 안 보는 값**(ID, 파일 경로 같은 것)은 그냥 글자 하나입니다.

```json
"id": "gin_fizz"          ← ID는 번역 안 함 (컴퓨터용 이름표)
"name": { "ko": …, "en": … }  ← 화면에 보이는 이름은 번역 필수
```

### 규칙 ② 계산할 수 있는 값은 사람이 쓰지 않는다 (파생값)

예를 들어 칵테일의 **난이도(tier)** 는 "기믹이 몇 개냐"로 정해집니다. 이걸 사람이 손으로 적으면 레시피를 고칠 때마다 같이 고쳐야 하고, 까먹으면 데이터가 어긋나죠.

그래서 **빌드할 때 자동으로 계산해서 넣습니다.**

| 자동 계산되는 값 | 계산 방법 |
| --- | --- |
| `tier` (난이도 T1~T5) | 기믹 개수로 결정 — **시트에서 직접 지정하면 그 값이 우선** |
| `unlock_day` (칵테일 해금일) | 재료들의 해금일 중 **가장 늦은 날** — **시트에서 직접 지정하면 그 값이 우선** |
| `scoring_items` (채점 항목 수) | 레시피에서 자동 계산 |
| `time_limit_sec` (제한 시간) | `20초 + 기믹수 × 8초` |
| `gimmick_count` (기믹 수) | 레시피 줄 수 + 믹스 여부 |

> 💡 **JSON에서 이 값들이 보여도 엑셀에는 (대부분) 없습니다.** 빌드가 붙여준 것이니 신경 쓰지 마세요.
> 단 `tier`와 `unlock_day`는 **"자동 계산 or 수동 지정"** 입니다. 칵테일 시트의 `tier_override`·`unlock_day_override` 칸을 비워두면 자동 계산되고, 값을 넣으면 **그 값이 그대로 정답**이 됩니다. 기믹 개수가 곧 체감 난이도는 아니고, 스토리상 특정 날에 열어야 하는 술도 있으니까요.

### 규칙 ③ `null`과 `""`는 다릅니다

| 표기 | 뜻 | 예시 |
| --- | --- | --- |
| `null` | **해당 없음** (그런 게 아예 없음) | `"garnish": null` = 가니시가 없는 칵테일 |
| `""` (빈 글자) | **조건 없음** (항상 참) | `"when": ""` = 조건 없이 무조건 실행 |

헷갈리기 쉬운데, 조건식 자리의 `""`는 "언제나 통과"라는 **적극적인 의미**입니다.

### 규칙 ④ 조건식(when)과 효과식(effects) — 게임 전체가 쓰는 공용 언어

이게 이 프로젝트에서 **가장 중요한 개념**입니다. 천천히 읽어주세요.

대본, 퀘스트, 엔딩, 취향, 주문 판정… 이 모든 곳에서 **똑같은 문법**으로 조건과 결과를 씁니다. 언어를 하나만 배우면 모든 파일을 다 읽을 수 있게 만든 거예요.

#### `when` = "언제 이게 벌어지나?" (조건)

```
day == 2                      3일차가 아니라 정확히 2일차일 때
affinity.chris >= 50          크리스 호감도가 50 이상일 때
flag.q_samho_honey_started    '삼호 벌꿀 퀘스트 시작' 표시가 켜져 있을 때
cocktail.abv >= 20            만든 칵테일 도수가 20도 이상일 때
cocktail.tag(달콤한)           만든 칵테일에 '달콤한' 태그가 붙어 있을 때
alive.haru                    하루가 살아있을 때
```

여러 조건을 겹치려면 `&&`(그리고)로 잇습니다.

```
flag.samho_calmed && cocktail.abv >= 20
→ '삼호가 진정됨' 표시가 켜져 있고 동시에 도수가 20 이상일 때
```

> ### ❗ "또는(OR)"은 없습니다
> 일부러 뺐습니다. `A 또는 B`를 허용하면 조건식이 금방 복잡해져서 아무도 못 읽게 되거든요.
> **"또는"이 필요하면 줄을 두 개로 나눠서 씁니다.** 각각 조건을 하나씩 갖는 두 줄로요.
> 이렇게 하면 데이터가 표로 봤을 때 항상 읽히고, 프로그램도 단순해집니다.

#### `effects` = "그래서 뭐가 바뀌나?" (결과)

```
affinity.chris += 2               크리스 호감도를 2 올린다
money += 50                       돈을 50 준다
flag.q_samho_honey_done = true    '벌꿀 퀘스트 완료' 표시를 켠다
unlock_recipe(bees_knees)         '비즈 니즈' 레시피를 해금한다
give(lime, 3)                     라임을 3개 준다
```

여러 개를 한 번에 하려면 `;`(세미콜론)으로 잇습니다.

```
affinity.samho += 10; unlock_recipe(bees_knees); flag.q_samho_honey_done = true
→ 삼호 호감도 +10, 비즈 니즈 해금, 완료 표시 켜기를 한꺼번에
```

#### 플래그(flag)가 뭔가요?

**게임이 기억해 두는 예/아니오 스위치**입니다. 딱 켜짐/꺼짐 두 가지 상태뿐이에요.

```
flag.q_samho_honey_started = true    ← 스위치를 켠다 (퀘스트 수주함)
```

한 번 켜두면 나중에 언제든 확인할 수 있습니다.

```
when: flag.q_samho_honey_done        ← "그 퀘스트 끝냈어?" 하고 물어보기
```

이 스위치 덕분에 **"3일차에 한 일이 8일차 대사를 바꾸는"** 연출이 가능해집니다.

> 💡 **프로그래머 메모**: 이 문법 덕분에 파서(해석기)는 딱 3개만 있으면 됩니다.
> ① 조건 판정기 ② 효과 적용기 ③ 씬-스텝 실행기. 새 기능이 생겨도 이 3개가 재사용됩니다.

## A-1. `cocktails.json` — 칵테일 정의 (18종)

게임의 핵심입니다. 어떤 칵테일이 있고, 어떻게 만들고, 얼마인지를 담습니다.

### 실제 데이터 (진피즈)

```json
{
  "id": "gin_fizz",
  "name": { "ko": "진피즈", "en": "Gin Fizz" },
  "price": 220,
  "abv": 8.0,
  "glass": "highball",
  "mix": "shake",
  "prep": null,
  "fill": "soda_water",
  "garnish": "lemon_slice",
  "color": "255,255,255",
  "tags": ["상큼한", "클래식", "청량한"],
  "flavor": { "ko": "진과 레몬, 그리고 '피즈' 하는 탄산 소리.", "en": "Gin, lemon, and that 'fizz' of carbonation." },
  "recipe": [
    { "action": "pour",    "ingredient": "gin",   "qty": 1.5, "unit": "oz"  },
    { "action": "squeeze", "ingredient": "lemon", "qty": 0.5, "unit": "oz"  },
    { "action": "powder",  "ingredient": "sugar", "qty": 1,   "unit": "tsp" }
  ],
  "unlock_when": null,
  "unlock_day_override": null,   // 값을 넣으면 해금일을 직접 지정
  "tier_override": null,        // 값을 넣으면 티어를 직접 지정
  "gimmick_count": 4,
  "tier": 3,
  "unlock_day": 1,
  "scoring_items": 8,
  "time_limit_sec": 52
}
```

### 항목별 설명

| 항목 | 뜻 | 쓸 수 있는 값 |
| --- | --- | --- |
| `id` | 컴퓨터용 이름표. **다른 파일이 이걸로 이 칵테일을 가리킵니다** | 영문 소문자+밑줄 |
| `name` | 화면에 보이는 이름 | `{ko, en}` |
| `price` | 판매가 (골드) | 숫자 |
| `abv` | 도수(%). **취향·분기 판정에 쓰입니다** | 숫자 |
| `glass` | 어떤 잔에 담는지 | `shelf_items.json`의 `kind:glass` ID |
| `mix` | 섞는 방식 | `build`(휘젓기) / `shake`(셰이커) / `stir`(스터) / `none`(안 섞음) |
| `prep` | 병을 어떻게 여는지 | `null`(열 것 없음) / `cap`(병뚜껑) / `cork`(코르크) |
| `fill` | 마지막에 잔을 채우는 음료 | 재료 ID 또는 `null` |
| `garnish` | 장식 (**v1.9부터 플레이어가 고르는 채점 항목**) | `shelf_items.json`의 `kind:garnish` ID 또는 `null` |
| `color` | 잔에 채워질 색 (빨강,초록,파랑) | `"255,255,255"` |
| `tags` | 맛 분류. **취향 판정이 이걸 봅니다** | 목록 |
| `flavor` | 메뉴판 설명 문구 | `{ko, en}` |
| `recipe` | **채점 정답표** (아래 상세) | 목록 |
| `unlock_when` | 퀘스트로 풀리는 칵테일이면 그 완료 플래그 | 조건식 또는 `null` |
| `unlock_day_override` | **해금일 직접 지정.** 비우면 재료에서 자동 계산 | 숫자 또는 `null` |
| `tier_override` | **티어 직접 지정.** 비우면 기믹 수로 자동 계산 | 1~5 또는 `null` |

### `recipe` 자세히 보기

한 줄이 "재료 하나를 넣는 행동" 하나입니다.

```json
{ "action": "pour", "ingredient": "gin", "qty": 1.5, "unit": "oz" }
```
→ **"진을 1.5온스 따른다"**

| `action` | 뜻 | 어떤 미니게임인지 |
| --- | --- | --- |
| `pour` | 따르기 | 술이 자동으로 흘러나오고, 목표선에서 탭해서 멈춤 |
| `squeeze` | 짜기 | 버튼을 누르고 있는 동안 즙이 나옴, 떼면 확정 |
| `powder` | 가루 넣기 | 스푼 단위로 탭해서 넣음 |

> ### ⭐ 가장 중요한 오해 방지
> **`recipe`는 "실행 순서표"가 아니라 "채점 정답표"입니다.**
>
> 플레이어는 이 순서대로 강제되지 않습니다. 플레이어가 **선반을 차례로 지나며 직접 고르고**, '제조 시작'을 누르면 **정해진 논리 순서**로 실행돼요.
>
> ```
> 메뉴 → ①잔 선반 → ②도구 선반 → ③가니시 선반 → ④재료 선반 → [제조 시작]
>        ◀────────── ▶ 화살표로 좌우 이동 (상단 탭으로 직접 점프도 가능) ──────────▶
> ```
>
> 각 화면에서 **◀이전으로 돌아가 다시 고를 수 있습니다**(선택은 유지). 단 **되돌아가도 제한 시간은 계속 흐릅니다** — 무한정 고민하지 못하게요.
>
> ```
> ① 병 개봉 → ② 따르기(베이스 먼저) → ③ 스퀴즈 → ④ 파우더 → ⑤ 믹스 → ⑥ 필업
> ```
>
> 이 순서는 **담은 순서와 무관하게 강제**됩니다. 왜냐고요? **술을 따르지도 않았는데 젓는 건 말이 안 되니까요.** 플레이어가 셰이커를 제일 먼저 담아도, 셰이킹은 항상 재료를 다 넣은 뒤(⑤)에 실행됩니다.
>
> 그리고 `recipe`는 **"정답이 뭐였는지"** 를 판정할 때 쓰입니다. 진을 1.5oz 넣어야 하는데 3oz 넣었다면 그만큼 점수가 깎이는 식이죠.

### 자동 계산되는 항목 (사람이 안 씀)

| 항목 | 진피즈의 값 | 계산 근거 |
| --- | --- | --- |
| `gimmick_count` | 4 | 레시피 3줄 + 믹스(shake) 1 |
| `tier` | 3 | 기믹 4개 → T3 |
| `unlock_day` | 1 | 진·레몬·설탕이 전부 1일차 해금이라 |
| `scoring_items` | 8 | 시간·잔·믹스·레시피3줄·필업·가니시 |
| `time_limit_sec` | 52 | 20 + 4×8 = 52초 |

### 전체 칵테일 18종

| 해금일 | 칵테일 |
| --- | --- |
| **1일차** | 진토닉(T1) · 진피즈(T3) · 생맥주(T1) · 병맥주(T1) · 레드와인(T1) · 샴페인(T1) |
| **3일차** | 스크류드라이버(T2) · 모스코뮬(T2) · 데킬라 선라이즈(T2) · 롱아일랜드 아이스티(T5) |
| **4일차** | 위스키 사워(T3) · 드라이 마티니(T2) · 바카디(T3) |
| **5일차** | 코스모폴리탄(T4) |
| **6일차** | 마가리타(T3) · 화이트레이디(T3) · 깔루아 밀크(T2) |
| **퀘스트** | 비즈 니즈(T3) — `unlock_day: 99` = 날짜로는 안 풀리고 퀘스트로만 해금 |

## A-2. `shelf_items.json` — 선반에 놓이는 모든 것 (40행) ⭐

**재료·잔·도구·가니시가 한 테이블입니다.** 원래는 재료(ingredients)와 아이템(items)이 따로였는데, 제조가 **선반 4단계 선택**으로 바뀌면서 넷 다 "선반에서 고르는 것"이 되어 합쳤습니다(v1.9).

### 실제 데이터

```json
{ "id": "gin",    "kind": "ingredient", "name": {"ko":"진"},     "category": "base", "color": "230,235,240",
  "sprite": null,          "unlock_day": 1, "unlock_when": null, "shop_price": null, "desc": {"ko":"…"} }

{ "id": "shaker", "kind": "tool",       "name": {"ko":"셰이커"}, "category": null,   "color": "",
  "sprite": "tool_shaker", "unlock_day": 1, "unlock_when": null, "shop_price": null, "desc": {"ko":"…"} }
```

### `kind` — 어느 선반에 놓이나

| `kind` | 개수 | 제조 단계 |
| --- | --- | --- |
| `glass` | 7 | ① 잔 선반 |
| `tool` | 3 | ② 도구 선반 |
| `garnish` | 5 | ③ 가니시 선반 |
| `ingredient` | 25 | ④ 재료 선반 |

### 항목별 설명

| 항목 | 뜻 |
| --- | --- |
| `kind` | **어느 선반 화면에 놓일지** 결정 |
| `category` | **재료일 때만.** 어떤 기믹이 나올지 결정 (아래) |
| `color` | 액체 렌더 RGB |
| `sprite` | 잔·도구·가니시의 그림 키 (재료는 `null`) |
| `unlock_day` | 며칠차부터 선반에 나오는지 |
| `unlock_when` | 퀘스트로 풀리는 것이면 그 완료 플래그 |
| `shop_price` | 노점 구매가 (`null`이면 안 팜) |

### `category` 9종 — 재료가 어떤 기믹으로 가나

| 분류 | 기믹 |
| --- | --- |
| `base` `liqueur` `wine_beer` `juice` `dairy` `syrup` | 따르기 |
| `fruit` | 스퀴즈 |
| `powder` | 파우더 |
| `mixer` | 필업 |

### ⭐ 핵심 개념 — "해금의 주체는 재료다"

이 게임에서 **"새 칵테일이 열린다"는 개념은 사실 없습니다.** 대신 **재료가 열립니다.**

```
3일차에 데킬라·보드카·럼·오렌지주스가 입고됨
   ↓ 그러면 자동으로
스크류드라이버, 데킬라 선라이즈, 모스코뮬… 이 만들 수 있게 됨
```

칵테일의 `unlock_day`는 기본적으로 **재료들의 해금일에서 자동 계산**됩니다. 그래서 기획자는 재료 입고일만 관리하면 되죠. (다만 **필요하면 칵테일 시트에서 직접 지정**할 수도 있습니다 — A-1의 `unlock_day_override` 참고.)

### 해금·상점가가 잔·도구·가니시에도 있는 이유

가니시(올리브·체리)는 실제 바에서 **소모품**입니다. 그래서 "4일차에 올리브 입고" 같은 설계가 가능해야 하죠. 잔·도구도 스토리상 나중에 들어오는 연출을 못 할 이유가 없고요.

> 💡 다만 **입고 화면(stock_in)에는 소모품(`ingredient`·`garnish`)만** 나옵니다. 잔·도구는 "상시 비치" 개념이라 입고 연출에 끼지 않아요.

### 퀘스트 재료는 어떻게 하나요?

실제로 들어있는 유일한 퀘스트 재료, **벌꿀 원액**입니다.

```json
{
  "id": "honey_syrup", "kind": "ingredient",
  "name": { "ko": "벌꿀 원액", "en": "Raw Honey" },
  "category": "syrup", "color": "235,180,60",
  "unlock_day": 99,
  "unlock_when": "flag.q_samho_honey_done",
  "shop_price": null,
  "desc": { "ko": "삼호의 창고에서 나온 진짜 꿀. 요즘 세상엔 금값이다." }
}
```

- `unlock_day: 99` = **날짜로는 절대 안 풀림** (게임은 13일차까지니까요)
- `unlock_when` = **이 조건이 참이 되면 풀림**
- `shop_price: null` = **돈으로는 못 삼.** 퀘스트로만 얻는 재료

### ⚠️ 통합의 대가 — kind를 잘못 넣는 실수

한 테이블이 되면서 `Cocktails`의 잔 칸에 실수로 재료 id를 넣는 게 **문법상 가능**해졌습니다. 그래서 빌드가 **참조 대상의 `kind`까지 대조**해서 잡습니다.

```
[칵테일] gin_fizz: 잔 칸에 kind=glass가 아닌 lemon 지정됨
```

### 도구 3종 자세히 ⭐

**제조 시스템의 핵심입니다.** ② 도구 선반에서 담으면, 그에 맞는 미니게임이 실행 순서에 편입됩니다.

| 도구 | ID | 미니게임 | 정답 기준 |
| --- | --- | --- | --- |
| 셰이커 | `shaker` | **셰이킹** — 위아래로 드래그, 스스로 멈춤 | `mix: shake`, 8회 근처 |
| 믹싱 글라스 & 바 스푼 | `mixing_glass` | **스터** — 원을 그리며 젓다 멈춤 | `mix: stir` 3바퀴 / `build` 1바퀴 |
| 따개 | `opener` | **병뚜껑**(3연타) 또는 **코르크**(천천히 2바퀴) | `prep` 값과 일치 |

> **코르크 기믹이 재밌는 지점**: 와인·샴페인은 **천천히 돌려야** 합니다. 급하게 돌리면 코르크가 부스러지고(💥) 그만큼 점수가 깎여요(품질 0.2~1.0). "조심스럽게 다루는 것"이 조작으로 표현된 부분입니다.

> **주의**: 코르크/뚜껑 병을 담았는데 따개를 안 담으면 '제조 시작'이 막힙니다. 병을 열 수가 없으니까요.

### 잔 7종 · 가니시 5종

- **잔**: `mug`(맥주잔) `wine` `flute` `highball` `collins` `rocks` `cocktail` — ① 화면에서 선택. 틀리면 채점 0점 항목
- **가니시**: `lime_wedge` `lemon_slice` `olive` `cherry` `orange_slice` — ③ 화면에서 선택. **"없음"도 하나의 선택지**

## A-4. `expressions.json` — 표정

이 파일만 구조가 조금 다릅니다. 목록`[ ]`이 아니라 **인물 ID로 찾아 쓰는 사전`{ }`** 형태예요.

```
expressions.json
 ├─ "luna"   ─┬─ "default" → 표정 정의
 │            └─ …
 ├─ "chris"  ─┬─ "default" → 표정 정의
 │            ├─ "success" → 표정 정의
 │            └─ "fail"    → 표정 정의
 └─ "common" → 랜덤 손님 공용 세트
```

표정을 만드는 방법이 **두 가지**입니다.

### 방법 ① `parts_anim` — 파츠 조합 애니메이션 (주요 인물)

얼굴을 **부위별로 쪼개서** 각각 애니메이션을 돌립니다. 눈은 깜빡이고, 입은 말할 때만 움직이는 식이에요.

```json
"luna": {
  "default": {
    "mode": "parts_anim",
    "sprite": null,
    "talk_anim": true,
    "parts": {
      "eyes":       { "clip": "luna_eyes_default",       "loop": "always" },
      "eyebrows":   { "clip": "luna_eyebrows_default",   "loop": "always" },
      "upper_face": { "clip": "luna_upper_face_default", "loop": "always" },
      "lower_face": { "clip": "luna_lower_face_default", "loop": "always_on_dialogue" },
      "body":       { "clip": "luna_body_default",       "loop": "always" }
    }
  }
}
```

**`loop` 값이 핵심입니다.**

| `loop` | 언제 재생되나 |
| --- | --- |
| `always` | 계속 반복 (눈 깜빡임 등) |
| `always_on_dialogue` | **대사 중일 때만 반복** ← 입 움직임이 이걸 씁니다 |
| `once` | 한 번만 |
| `none` | 정지 (첫 프레임 고정) |
| `special_on_dialogue` | 대사 중 특수 연출 |

> 💡 **입이 움직이는 원리**: `lower_face`(입 주변)에 `always_on_dialogue`를 걸어두면, 대사가 출력되는 동안만 입 애니메이션이 돌아갑니다. 말이 끝나면 자동으로 멈추고요. 대사마다 입 애니를 일일이 지정할 필요가 없습니다.

### 방법 ② `sprite` — 그림 한 장 교체 (단순 표정)

```json
"chris": {
  "success": { "mode": "sprite", "sprite": "chris_success", "talk_anim": false, "parts": null }
}
```

그냥 그림을 갈아끼웁니다. 랜덤 손님(`common` 세트)은 전부 이 방식이에요. 만들 그림이 많으니 단순하게 갑니다.

> **왜 두 방식을 섞나요?** 자주 나오고 감정 표현이 중요한 인물(루나·크리스·단골)은 파츠 애니로 생동감 있게, 잠깐 스쳐가는 손님은 그림 한 장으로 — **작업량과 퀄리티의 타협**입니다.

## A-9. `tastes.json` — 캐릭터 취향 ⭐ (10행)

**이 게임에서 가장 재미있는 시스템입니다.** 천천히 봐주세요.

### 실제 데이터

```json
{ "character_id": "port",  "seq": 1, "when": "cocktail.id == gin_fizz",  "tier": "love",    "note": "수십 년 진피즈 한 우물" }
{ "character_id": "port",  "seq": 2, "when": "cocktail.tag(클래식)",      "tier": "good",    "note": "옛날 사람" }

{ "character_id": "aili",  "seq": 1, "when": "cocktail.id == champagne",  "tier": "love",    "note": "새벽술은 무죄" }
{ "character_id": "aili",  "seq": 2, "when": "cocktail.tag(화사한)",      "tier": "good" }
{ "character_id": "aili",  "seq": 3, "when": "cocktail.abv >= 25",        "tier": "dislike", "note": "의사로서 독주는 사양" }
```

### 작동 원리 — "첫 번째로 맞는 게 이긴다"

`seq` 번호 **순서대로 위에서부터 확인**하다가, **처음으로 조건이 맞는 줄에서 멈춥니다.**

아일리에게 **샴페인**을 줬다고 해봅시다.

```
seq 1: "샴페인이야?"        → 맞음! → tier = love ✓ (여기서 끝, 아래는 안 봄)
seq 2: (확인 안 함)
seq 3: (확인 안 함)
```

아일리에게 **롱아일랜드 아이스티(도수 25 이상)** 를 줬다면?

```
seq 1: "샴페인이야?"        → 아님
seq 2: "'화사한' 태그 있어?" → 아님
seq 3: "도수 25 이상이야?"   → 맞음! → tier = dislike ✓
```

### `tier` 4단계

| 값 | 뜻 |
| --- | --- |
| `love` | 정말 좋아함 |
| `good` | 좋아함 |
| `ok` | 무난함 (아무 줄에도 안 걸리면 자동으로 이것) |
| `dislike` | 싫어함 |

### ⭐⭐ 상황부 취향 — 이 시스템의 진짜 목적

여기서부터가 핵심입니다. **같은 사람이 상황에 따라 다른 걸 좋아하게** 만들 수 있어요.

```json
{ "character_id": "samho", "seq": 1, "when": "flag.samho_calmed && cocktail.abv >= 20", "tier": "dislike",
  "note": "배려 루트 이후엔 독주를 밀어냄 — 상황부 취향 데모" }
{ "character_id": "samho", "seq": 2, "when": "cocktail.abv >= 20", "tier": "love",
  "note": "독한 술이 기본 취향" }
```

읽어보면 이렇습니다.

| 상황 | 삼호에게 독주(20도↑)를 주면 |
| --- | --- |
| **평소** | seq 1 조건에서 `flag.samho_calmed`가 꺼져 있어 통과 → seq 2에 걸림 → **love** 😊 |
| **'진정됨' 이후** | seq 1이 통째로 맞음 → **dislike** 😟 |

즉 **플레이어가 삼호를 배려하는 선택을 한 뒤로는, 독주를 주면 오히려 싫어합니다.**

> ### 왜 이게 중요한가요?
> 보통 게임에서 "이 캐릭터의 최애 음료는 X" 하고 고정해 두면, 플레이어는 한 번 알아내고 나서 계속 X만 줍니다. 재미가 금방 떨어지죠.
>
> 하지만 이 구조에서는 **"이 사람이 지금 어떤 상태인지"** 를 읽어야 합니다. 어제까지 좋아하던 걸 오늘은 싫어할 수 있으니까요. **관계가 살아있는 느낌**이 여기서 나옵니다.
>
> 그리고 놀라운 건, 이게 **새로운 문법 없이** 가능하다는 점입니다. 조건식(`when`)에 플래그를 하나 섞은 것뿐이에요. §3의 공용 언어를 만들어 둔 보람이 여기서 나옵니다.

## A-10. `dossier.json` — 단골 수첩 ⭐ (20행)

바 화면의 **📒 단골 수첩** 탭에 뜨는 인물 정보입니다. **호감도가 오를수록 한 줄씩 열립니다.**

### 실제 데이터

```json
{ "character_id": "samho", "min_affinity": 35, "kind": "history", "when": null,
  "text": { "ko": "부모가 데려온 일곱 동생을 혼자 돌보고 있다." } }

{ "character_id": "samho", "min_affinity": 0, "kind": "recent",
  "when": "flag.samho_refused_drink",
  "text": { "ko": "내일 노란 꽃을 보여주겠다고 약속했다." } }
```

### 항목별 설명

| 항목 | 뜻 |
| --- | --- |
| `min_affinity` | **이 호감도 이상일 때 공개.** 0이면 만나자마자 보임 |
| `kind` | `desc`(소개) / `taste`(취향) / `history`(과거사) / `secret`(숨겨진 이야기) / `recent`(근황) |
| `when` | 조건부 공개. 주로 `recent`에 씀 — 스토리 진행에 따라 근황이 바뀐다 |
| `text` | 수첩에 표시될 문장 |

### 공개 단계 (시드 기준 — 시트에서 조절 가능)

```
아직 안 만남   →  ??? (실루엣만)
만남 + 호감도 9 이하  →  이름만
호감도 10  →  📋 한 줄 소개
호감도 20  →  🍸 취향
호감도 35  →  📖 과거사
호감도 50  →  🗝 숨겨진 이야기
```

**잠긴 항목은 숨기지 않고 "🔒 호감도 35에 열림"으로 보여줍니다.** 이게 핵심이에요 — 플레이어가 *"아, 호감도를 올리면 이 사람에 대해 더 알 수 있구나"* 하고 **시스템의 존재 자체를 알게** 되니까요.

> ### ⚠️ Tastes 시트와 헷갈리지 마세요
> - **`tastes.json`** = 실제 **판정 규칙**. "이 술을 주면 호감도가 얼마나 오르나"를 계산
> - **`dossier.json`의 `kind: taste`** = 플레이어에게 **보여주는 문장**. "독한 술을 동경한다" 같은 소개문
>
> 둘은 따로 관리됩니다. 취향 규칙을 바꿨으면 수첩 문장도 같이 손봐야 해요.

### 💡 근황(recent)이 이야기를 따라간다

`when`을 걸면 **같은 인물의 수첩이 스토리 진행에 따라 바뀝니다.** 데모의 삼호가 그 예:

```
따라준 루트  →  "취한 채로 꽃을 가지러 나갔다. …밖이 소란스럽다."
거절한 루트  →  "내일 노란 꽃을 보여주겠다고 약속했다."
```

수첩이 단순한 도감이 아니라 **불안감을 증폭시키는 장치**가 되는 거죠.

## B-3. `grade_payout` — 등급별 정산 (매출 + 팁) ⭐

```json
{ "excellent": {"revenue_mult": 1.0,  "tip_mult": 0.2},
  "good":      {"revenue_mult": 1.0,  "tip_mult": 0.0},
  "decent":    {"revenue_mult": 1.0,  "tip_mult": 0.0},
  "poor":      {"revenue_mult": 1.0,  "tip_mult": 0.0},
  "sewage":    {"revenue_mult": -1.0, "tip_mult": 0.0} }
```

- `revenue_mult` = **술값 배율.** 음수면 **배상**(오히려 돈을 물어줍니다)
- `tip_mult` = 술값 대비 팁 비율. 손님 성격의 `tip_mult`가 한 번 더 곱해집니다

**실제 계산 (180G짜리 진토닉 기준)**

| 등급 | 매출 | 팁 | 실수령 |
| --- | --- | --- | --- |
| excellent | +180 | +36 | **+216G** |
| good | +180 | 0 | +180G |
| decent | +180 | 0 | +180G |
| poor | +180 | 0 | +180G |
| **sewage** | **−180** | 0 | **−180G** |
| **주문과 다른 술** | **−180** | 0 | **−180G** |

> ### 배상은 왜 sewage와 오제조만인가요?
> **"마실 수 없는 걸 내놨다"** 는 두 경우만 손님에게 물어주는 겁니다. `poor`는 맛이 없을 뿐 마실 수는 있으니 술값은 받되 **팁이 없죠**. 등급을 낮게 받을수록 벌이가 나빠지긴 하지만, 실수 한 번에 파산하진 않게 한 균형입니다.
>
> 주문과 다른 술의 배율은 `balance.config.wrong_cocktail_revenue_mult`(−1.0)가 따로 담당합니다.

## B-4. `affinity_matrix` — 취향 × 등급 → 호감도 ⭐

**이 표 하나가 게임의 감정 시스템 전부**입니다.

| 취향 \ 등급 | excellent | good | decent | poor | sewage |
| --- | --- | --- | --- | --- | --- |
| **love** (정말 좋아함) | **+6** | +4 | +1 | −1 | −2 |
| **good** (좋아함) | +4 | +3 | +1 | −1 | −2 |
| **ok** (무난) | +2 | +1 | 0 | −1 | −3 |
| **dislike** (싫어함) | +1 | 0 | −1 | −2 | −4 |
| **miss** (주문과 딴판) | **−4** | −4 | −4 | −4 | −4 |

### 이 표에서 읽어야 할 것

**① 잘 만드는 것만으로는 부족합니다.**
`dislike` × `excellent` = **+1**밖에 안 됩니다. 완벽하게 만들어도 그 사람이 싫어하는 술이면 소용없어요.

**② 주문을 잘못 읽으면 실력이 무의미합니다.**
`miss` 줄은 **전부 −4**입니다. 아무리 완벽하게 만들어도, 그 사람이 원한 게 아니면 −4예요.

**③ 최고 보상은 "좋아하는 걸 완벽하게"입니다.**
`love` × `excellent` = **+6**. 이게 최대치입니다.

> ### 💡 이 표가 말하는 게임 철학
> **"손기술(제조)"보다 "사람 읽기(선택)"가 더 중요하다.**
>
> 세로축(취향)은 **누구에게 무엇을 줄지 = 머리와 마음**의 영역이고,
> 가로축(등급)은 **얼마나 잘 만들지 = 손기술**의 영역입니다.
>
> 표를 보면 세로축의 진폭(+6 ~ −4)이 가로축보다 큽니다. **의도적입니다.** 이 게임은 바텐딩 시뮬레이터가 아니라, 사람 이야기를 듣는 게임이니까요.

# C. 스케줄 — 하루가 어떻게 흘러가나

## C-1. `days.json` — 일차 정의 (3일치)

```json
{
  "day": 3,
  "label": { "ko": "삼호와 아일리", "en": "Samho & Aili" },
  "start_phase": "commute_in",
  "bgm_street": "bgm_street_night",
  "bgm_bar": "bgm_bar_main",
  "note": "입고 4종(데킬라·보드카·럼·OJ). 밤: 습격의 꿈 2"
}
```

| 항목 | 뜻 |
| --- | --- |
| `day` | 일차 번호 |
| `label` | 그날의 제목 (로딩 화면 등에 표시) |
| `start_phase` | **그날이 어디서 시작하는지** |
| `bgm_street` / `bgm_bar` | 거리·바 배경음악 |

`start_phase`가 다른 이유가 재밌습니다.

- **1일차(튜토리얼)**: `bar` — 출근길·입고 없이 **바에서 바로 시작**합니다. 처음이라 배울 게 많으니 군더더기를 뺀 거예요.
- **2일차부터**: `commute_in` — 출근길부터 정식 사이클이 돕니다.

### 하루의 전체 흐름

```
출근길 19:00  →  입고(stock_in)  →  개점 대화 + OPEN 간판  →  1부 일반 영업
    →  2부 스토리 손님  →  정산  →  퇴근길 02:00  →  집(테라스 대화)  →  꿈  →  다음 날
```

### 💡 1부는 자동으로 시작하지 않습니다 (v1.9)

바에 들어가면 바로 손님이 오는 게 아니라, 이 순서를 거칩니다.

```
바 진입 → phase="bar_open" 씬 재생 (크리스와 짧은 대화)
       → OPEN 간판이 화면에 뜸 ("준비 중" 상태)
       → 플레이어가 간판을 클릭 → "영업 시작"으로 뒤집힘
       → 그제서야 1부 손님들(random_waves + regular_slots)이 들어오기 시작
```

**왜 이렇게 하나요?** 영업을 여는 행위를 플레이어가 직접 하면 "내 가게를 연다"는 감각이 생깁니다. 그리고 그 직전에 크리스와 나누는 짧은 대화가 **그날의 목표와 마음가짐을 알려주는 자리**가 됩니다.

예시 — 2일차 개점 대화(`d2_bar_open`):

> 크리스: 오늘부터는 손님을 직접 받는다. 어제 배운 대로 할 수 있겠지?
> 루나: 코스터를 먼저 내고, 주문을 받고, 만들어서 코스터 위에 올린다.
> 크리스: …외우긴 잘 외웠군. 손이 따라오는지는 해봐야 알겠지만.
> 크리스: **좋아, 시작해보자. 간판 걸어라.**

마지막 대사가 **크리스의 말**인 것에 주의하세요. §3의 "루나 대사 규칙"대로, 플레이어가 행동할 차례(간판 클릭) 직전에는 루나가 말하지 않습니다.

## C-2. `random_waves.json` + `regular_slots.json` — 1부 손님 스폰표 (7행 + 1행)

1부에 **손님이 몇 시에 몇 명 오는지**를 정합니다. v2.0부터 **두 파일**입니다 — 만지는 사람이 다르기 때문이에요.

**`random_waves.json`** — 이름 없는 랜덤 손님 (System 파일의 RandomWaves 시트, 운영 담당):

```json
{ "day": 3, "seq": 1, "tier": 2, "personality": "chatty", "delay_sec": 0, "max_rounds": 1 }
```

**`regular_slots.json`** — 단골 방문 (Narrative 파일의 RegularSlots 시트, 서사 담당):

```json
{ "day": 3, "seq": 4, "character": "port", "tier": 3, "delay_sec": 40, "max_rounds": 1,
  "branch_choice": false, "cameo_scene": "d3_cameo_port" }
```

| 항목 | 뜻 |
| --- | --- |
| `seq` | 그날 몇 번째 손님인지 — **두 파일이 번호를 나눠 씁니다.** 게임은 둘을 합쳐 seq 순으로 스폰 (위 예시: 랜덤 3명 뒤 4번째로 포트 등장) |
| `tier` | 주문할 칵테일의 난이도대 (T1~T5) |
| `personality` | 성격 (`personalities.json`) — 랜덤 손님 전용 |
| `character` | 단골 슬롯 전용, **필수** — 누가 오는지 |
| `delay_sec` | 앞 손님으로부터 **몇 초 뒤에 올지** |
| `max_rounds` | 몇 잔이나 주문하는지 |
| `branch_choice` | 분기 선택지가 붙는 슬롯인지 |
| `cameo_scene` | 단골이 착석하면 재생할 씬 |

> 💡 **왜 나눴나요?** 랜덤 손님의 수·간격·티어는 **난이도 튜닝**(운영 담당의 영역)이고, 단골이 언제 들르는지는 **이야기의 사건**(서사 담당의 영역)입니다. 한 시트에 있으면 두 사람이 같은 파일을 두고 충돌해요.

> 💡 **카메오의 의도**: 1부는 원래 이름 없는 손님들의 기믹 플레이 구간인데, 가끔 단골이 섞여 들어오면 "이 바가 진짜 동네 가게구나" 하는 느낌이 납니다. 2부의 무거운 이야기를 1부에서 살짝 예고하는 역할도 하고요.

### 한적한 슬럼가 무드

`delay_sec`이 **35~50초**로 꽤 깁니다. 하루 손님도 최대 4명뿐이고요. 손님이 밀려드는 바쁜 가게가 아니라 **"한산한 뒷골목 바"** 를 의도한 설정입니다.

## C-3. `spots.json` — 위치 프리셋 (9개)

```json
{ "id": "bar_door", "area": "street", "desc_ko": "바 '언노운' 정문 앞", "note": "출근 도착점 / 퇴근 출발점" }
```

거리에서의 위치를 **좌표(x, y) 대신 이름표로** 관리합니다. `area`는 `street`(큰길) / `alley`(골목) 두 종류.

> 💡 **왜 좌표를 안 쓰나요?** 배경 그림이 수정되면 좌표가 전부 어긋납니다. 하지만 "바 정문 앞"이라는 **이름**은 그림이 바뀌어도 그대로예요. 기획자도 숫자 대신 말로 지정할 수 있고요.

## C-4. `interact_points.json` — 거리 상호작용 지점 (11개)

거리에서 **플레이어가 조사할 수 있는 지점**입니다.

```json
{
  "id": "p_news_d2",
  "spot": "street_board",
  "kind": "object",
  "phase": "commute_in",
  "when": "day == 2",
  "scene_or_shop": "d2_news",
  "selection": "once",
  "note": "전광판 뉴스(세계관 떡밥)"
}
```

| 항목 | 뜻 |
| --- | --- |
| `spot` | 어느 위치에 있는지 (`spots.json`) |
| `kind` | `object`(연출) / `shop`(발주 상점) / `npc`(대화 상대) |
| `phase` | `commute_in`(출근길) / `commute_out`(퇴근길) / `both` |
| `when` | 조건. **이 예시는 2일차에만 나타납니다** |
| `scene_or_shop` | 조사했을 때 재생할 씬 또는 열 상점 |
| `selection` | 반복 규칙 (아래) |

### `selection` 4종

| 값 | 뜻 |
| --- | --- |
| `once` | 딱 한 번만 |
| `repeat` | 몇 번이고 반복 가능 |
| `sequential` | 순서대로 다음 내용 (1번→2번→3번) |
| `conditional` | 조건에 맞는 것만 |

> 💡 퀘스트의 `interact:p_lost_box` 목표가 바로 이 `id`를 가리킵니다. 데이터끼리 이렇게 연결돼요.

# D. 성장과 결말

## D-1. `quests.json` — 퀘스트 (2개)

이 파일만 **두 묶음**으로 되어 있습니다. `quests`(퀘스트 정보) + `stages`(단계별 목표).

```json
{
  "quests": [
    {
      "id": "samho_honey",
      "title": { "ko": "진짜 벌꿀", "en": "The Real Honey" },
      "kind": "side",
      "reward_effects": "affinity.samho += 10; unlock_recipe(bees_knees); flag.q_samho_honey_done = true",
      "note": "day3 삼호 거래 — 진피즈 제공 시 완료. 히든 레시피 '비즈 니즈' 해금"
    }
  ],
  "stages": [
    {
      "quest_id": "samho_honey",
      "stage": 1,
      "goal": "serve:gin_fizz",
      "when": "flag.q_samho_honey_started",
      "on_complete": ""
    }
  ]
}
```

### 퀘스트의 일생 (4단계)

```
① 수주      대화 중 선택지 "네" → flag.q_samho_honey_started = true (스위치 켜짐)
     ↓
② 목표      goal: "serve:gin_fizz"  ← 진피즈를 제대로 서빙하면 자동으로 감지
     ↓
③ 단계 진행  stage가 여러 개면 하나씩 넘어감 (이 퀘스트는 1단계짜리)
     ↓
④ 보상      마지막 단계를 끝낸 순간 reward_effects가 딱 한 번 실행
```

### `goal` 문법 2종

| 문법 | 뜻 | 예시 |
| --- | --- | --- |
| `serve:<칵테일ID>` | 그 칵테일을 정상 서빙하면 완료 | `serve:gin_fizz` |
| `interact:<포인트ID>` | 거리의 그 지점을 조사하면 완료 | `interact:p_lost_box` |

> **"정상 서빙"의 기준**: 오제조(엉뚱한 술)나 `sewage` 등급은 인정되지 않습니다. 대충 만들어 던져주고 퀘스트를 깰 수는 없어요.

### 보상 설계 — 재료와 레시피는 다르게 처리합니다

| 보상 종류 | 방법 | 언제 반영되나 |
| --- | --- | --- |
| 호감도·돈·평판 | `reward_effects`에 `affinity.x += n` | **즉시** |
| **레시피 해금** | `reward_effects`에 `unlock_recipe(id)` | **즉시** 메뉴에 등장 |
| **재료 해금** | `reward_effects`가 아니라 **`shelf_items.json`의 `unlock_when`** | **다음 날 입고 화면**에 등장 |

> ### 왜 재료만 다음 날인가요?
> **연출 때문입니다.** 재료에는 "입고"라는 단계가 있어요. 손님이 "구해다 주지" 하고 약속했으면, **다음 날 가게에 도착하는 게 자연스럽습니다.** 그 자리에서 재료가 뿅 나타나면 이상하죠.
>
> 반면 레시피는 **지식**이라 즉시 알게 되는 게 맞습니다. "이렇게 만드는 거야" 하고 배우면 바로 아는 거니까요.

### 🎬 이 둘이 만나면 이런 경험이 됩니다

벌꿀 퀘스트를 실제로 깨면 무슨 일이 벌어지는지 따라가 봅시다. `bees_knees`(비즈 니즈)의 레시피는 **진 + 벌꿀 원액 + 레몬**입니다.

```
[3일차 밤] 퀘스트 완료
   · unlock_recipe(bees_knees)     → 메뉴에 '비즈 니즈'가 바로 나타남 ✓
   · flag.q_samho_honey_done = true

   그런데 만들려고 하면?
   → 벌꿀 원액(honey_syrup)이 아직 선반에 없음. 못 만듦.
   → 메뉴에는 보이는데 만들 수는 없는 상태

[4일차 입고 화면]
   honey_syrup의 unlock_when(flag.q_samho_honey_done)이 참이 됨
   → 벌꿀 원액이 입고됨 📦
   → 이제 진짜로 비즈 니즈를 만들 수 있음 ✓
```

**"레시피는 배웠지만 재료가 아직 안 왔다"** 는 하룻밤의 기다림이 생깁니다. 이건 버그가 아니라 **의도된 연출**이에요. 삼호가 창고에서 꿀을 가져오는 시간인 셈이죠.

그리고 이 모든 게 **코드 한 줄 없이** 데이터 두 칸(`unlock_recipe` + `unlock_when`)으로 표현됐다는 게 이 구조의 힘입니다.

### 연계 퀘스트 만들기

`reward_effects`가 마지막에 `flag.q_samho_honey_done = true`를 켭니다. 이 스위치를 나중에 확인하면 **연계 이야기**를 만들 수 있어요.

```
when: flag.q_samho_honey_done     → "지난번 벌꿀은 잘 썼나?" 하는 후속 대사
when: !flag.q_samho_honey_done    → 그 일이 없었던 것처럼 진행
```

### 현재 들어있는 퀘스트 2개

| ID | 제목 | 목표 타입 | 보상 |
| --- | --- | --- | --- |
| `samho_honey` | 진짜 벌꿀 | `serve:gin_fizz` | 삼호 +10, 히든 레시피 '비즈 니즈' |
| `lost_box` | 노점상의 잃어버린 상자 | `interact:p_lost_box` | 돈 +50, 라임 3개 |

## D-2. `order_rules.json` — 분기 주문 판정표 (4행)

**2부의 애매한 주문**을 판정하는 표입니다. "뭘 만들어 냈느냐"가 이야기를 가릅니다.

```json
{ "order_id": "d4_samho_dilemma", "seq": 1, "when": "cocktail.abv >= 20",
  "verdict": "fulfill", "effects": "flag.samho_drunk = true",  "note": "독한 술 → 취함 → 사망 루트" }

{ "order_id": "d4_samho_dilemma", "seq": 2, "when": "cocktail.abv <= 5 && grade >= good",
  "verdict": "care",    "effects": "flag.samho_calmed = true; affinity.samho += 2" }
```

`tastes.json`과 똑같이 **`seq` 순서대로 확인해서 처음 맞는 줄이 이깁니다.**

| `verdict` | 뜻 |
| --- | --- |
| `fulfill` | 요구대로 들어줌 |
| `care` | 요구 대신 **배려**함 |
| `partial` | 어중간함 |
| `miss` | 완전히 빗나감 |

### 이 표가 하는 일 — 삼호의 생사

4일차에 삼호가 술을 청합니다. 그런데 그는 지금 취하면 안 되는 상태예요.

| 플레이어의 선택 | 판정 | 결과 |
| --- | --- | --- |
| 독한 술(20도↑)을 줌 | `fulfill` | `flag.samho_drunk` → **사망 루트** |
| 약한 술(5도↓)을 잘 만들어 줌 | `care` | `flag.samho_calmed` + 호감도 +2 → **생존** |

> ### ⭐ 이 게임의 정체성이 여기 있습니다
> 보통 게임에서 이런 선택은 **"A를 선택한다 / B를 선택한다"** 하는 대사 선택지로 처리합니다.
>
> 하지만 이 게임에서는 **"어떤 술을 만들어 내놓느냐"** 가 곧 선택입니다. 플레이어는 "삼호를 살릴까?" 라는 버튼을 누르는 게 아니라, **"이 사람 지금 상태를 보니 독한 걸 주면 안 되겠다"** 고 스스로 판단해서 약한 술을 만들어야 해요.
>
> 그리고 그 결과가 **취향 시스템에도 연결됩니다.** `flag.samho_calmed`가 켜지면, `tastes.json`의 삼호 seq 1이 발동해서 그 뒤로는 독주를 싫어하게 되죠. **하나의 선택이 여러 시스템을 타고 번져나갑니다.**

## D-3. `endings.json` — 엔딩 (5종)

```json
[
  { "priority": 1, "id": "bad_1",    "when": "flag.rios_accepted", "scene_id": "ed_bad1",    "note": "벡터 이전 수락 → 병기화" },
  { "priority": 2, "id": "happy_1",  "when": "affinity.aili >= 100 && affinity.tom >= 100 && affinity.port >= 100 && affinity.sunha >= 100", "scene_id": "ed_happy1", "note": "벡터 고발, 전체 생존" },
  { "priority": 3, "id": "happy_2",  "when": "affinity.aili >= 100 && affinity.tom >= 100 && affinity.port >= 100", "scene_id": "ed_happy2", "note": "언노운 이사, 전체 생존" },
  { "priority": 4, "id": "normal_1", "when": "alive.haru && affinity.haru >= 100", "scene_id": "ed_normal1", "note": "하루 루트, 크리스 사망" },
  { "priority": 5, "id": "bad_2",    "when": "", "scene_id": "ed_bad2", "note": "폴백 — 납치" }
]
```

### 작동 원리 — "폭포 판정"

물이 위에서 아래로 떨어지듯, **`priority` 1번부터 순서대로 확인**해서 **처음 조건이 맞는 엔딩으로 확정**됩니다.

```
1번 확인: 벡터 이전을 수락했나?          → 했으면 여기서 끝 (bad_1)
2번 확인: 아일리·톰·포트·선하 전부 100?   → 맞으면 여기서 끝 (happy_1)
3번 확인: 아일리·톰·포트 100?             → 맞으면 여기서 끝 (happy_2)
4번 확인: 하루가 살아있고 호감도 100?      → 맞으면 여기서 끝 (normal_1)
5번 확인: when이 ""(무조건)              → 위에서 아무것도 안 걸리면 여기 (bad_2)
```

### 이 구조에서 읽을 수 있는 것

**① 최악의 선택은 다른 모든 걸 덮어씁니다.**
`bad_1`이 1순위라, 벡터 이전을 수락하면 호감도를 아무리 쌓았어도 병기화 엔딩입니다.

**② 해피엔딩은 계단식입니다.**
`happy_1`은 4명 전부 100, `happy_2`는 3명만 100. **한 명 차이로 결말이 갈립니다.**

**③ 맨 아래는 안전망입니다.**
`bad_2`의 `when`이 `""`(항상 참)이라, **아무 조건도 못 채워도 엔딩은 반드시 나옵니다.** "엔딩이 안 뜨는 버그"가 구조적으로 불가능해요.

> 💡 **빌드 검사기가 여기를 검증합니다**: "호감도를 최대로 올려도 100에 도달 가능한가?"를 시뮬레이션해서 알려줍니다. 도달 불가능한 엔딩이 있으면 밸런스를 고쳐야 하니까요.

## E-1. Scene (씬) — 대사 한 덩어리

## E-2. Step (스텝) — 한 줄의 동작

씬 안에는 **스텝이 줄줄이** 들어 있습니다. 대사 한 줄, 등장 하나가 각각 스텝이에요.

```json
{
  "seq": 3,
  "type": "say",
  "actor": "chris",
  "arg": "default",
  "text": { "ko": "루나.", "en": "Luna." },
  "when": null,
  "effects": null,
  "sync": "wait"

```
→ **"크리스가 기본 표정으로 '루나.' 라고 말한다"**

| 항목 | 뜻 |
| --- | --- |
| `seq` | 순서 |
| `type` | 무슨 동작인지 (아래 13종) |
| `actor` | 누가 |
| `arg` | 타입별 추가 정보 (표정 이름, 방향, 칵테일 ID 등) |
| `text` | 대사 (`{ko, en}`) |

| `effects` | 이 스텝이 일으키는 효과 |
| `sync` | `wait`(끝나야 다음) / `no_wait`(동시에 진행) |

### `type` 13종 전체

| 그룹 | `type` | 하는 일 | `arg` 예시 |
| --- | --- | --- | --- |
| **대사** | `say` | 대사 출력 | 표정 이름 (`"default"`) |

| | `craft` | 제조 미니게임 시작 | `"order"` (주문한 걸로) |

| | `effect` | 대사 없이 효과만 | |

`d1_tutorial_chris` 씬의 진행입니다 (총 76스텝 중 일부).

```json
{ "seq":  1, "type": "timeline", "arg": "tl_intro_lab", "sync": "wait" }
{ "seq":  2, "type": "enter", "actor": "chris", "arg": "R" }
{ "seq":  3, "type": "say",   "actor": "chris", "arg": "default", "text": { "ko": "루나." } }

…

             "text": { "ko": "드라이 마티니 한 잔. 흔들지 말고 저어서." } }
```

읽어보면 이렇습니다.

1. 연구소 컷씬을 재생하고 (끝날 때까지 기다림)

6. 서빙하고 판정받습니다

### `order`의 `exact:` 가 중요합니다

| 주문 방식 | 뜻 | 어디서 쓰나 |
| --- | --- | --- |
| `exact:<칵테일ID>` | **정확히 그 이름을 말함** | 1부 랜덤 손님, 튜토리얼 |
| (애매한 주문) | 분위기만 말함 → 유추 필요 | 2부 스토리 손님 |

튜토리얼 뒷부분에서 크리스가 이걸 직접 설명합니다.

> 크리스: "방금은 내가 원하는 칵테일을 정확히 주문했지만, 손님에 따라서는 주문을 애매하게 하거나…"
> 루나: "그러면 제 마음대로 만들어 주면 되는 건가요?"
> 크리스: "그래도 되겠지. 하지만 아무 생각 없이 만들어서는 안 돼. 애매한 주문이라도 최대한 **의도**를 파악하려고 해 봐."

**게임의 핵심 규칙을 튜토리얼 대사로 가르치는 구조**입니다.

## E-3. Choice (선택지)

`choices`는 씬 밖에 따로 모아두고, `choice` 스텝이 키로 불러 씁니다.

```json
"choices": {
  "ch_d1_home": [
    { "seq": 1, "text": { "ko": "지낼 만해요." },     "when": null, "effects": "affinity.chris += 2", "goto": null },
    { "seq": 2, "text": { "ko": "…아직 모르겠어요." }, "when": null, "effects": "affinity.chris += 1", "goto": null }
  ]
}
```

| 항목 | 뜻 |
| --- | --- |
| `text` | 선택지 문구 |
| `when` | 이 선택지가 **보일 조건** (조건부 선택지 가능) |
| `effects` | 골랐을 때의 효과 |
| `goto` | 다른 씬으로 점프 (`null`이면 그냥 이어감) |

> 💡 선택지는 **호감도가 움직이는 주요 지점**입니다. 위 예시는 크리스에게 "지낼 만해요"라고 하면 +2, "모르겠어요"라고 하면 +1이에요. **정답이 있는 건 아니고**, 마음을 여는 쪽이 조금 더 오릅니다.

### 루나 대사 규칙 (빌드가 강제합니다)

> **제조·서빙·선택지 바로 직전 스텝에 루나의 대사를 넣으면 빌드가 실패합니다.**

왜냐면 그 자리는 **플레이어가 행동할 차례**이기 때문입니다. 루나(플레이어 캐릭터)가 먼저 말해버리면 플레이어의 몰입이 끊겨요. 행동을 유도하고 싶으면 **상대방 대사로** 해야 합니다.

```
❌ 루나: "만들어 드릴게요." → [제조 시작]
✅ 크리스: "드라이 마티니 한 잔." → [제조 시작]
```

현재 **바 2부 손님 파트**는 이전 엔진에서 쓰던 **진짜 대본 634스텝을 이식**한 것입니다. 가안이 아니라 실제 완성 대본이에요.

```
├─ 정산 ────────────────────────────────────────────────
│  balance.config → 매출·팁·평판 집계
├─ 퇴근길 02:00 ────────────────────────────────────────
│  interact_points.json    → phase: commute_out 지점들
│                   (lost_box 퀘스트 회수 지점 등)
├─ 집 · 꿈 ─────────────────────────────────────────────
│  script/day_3   → phase: home (테라스 강제 대화)
│                 → phase: dream (습격의 꿈 2)
└─ day 4로 ────────────────────────────────────────────
   ingredients.unlock_when이 켜진 재료가 있으면
   다음 입고 화면에 등장
```

그리고 **13일차가 끝나면** `endings.json`이 폭포 판정으로 결말을 정합니다. 이 13일 동안 쌓인 호감도의 총합이 결과가 되는 거예요.

# G. 자주 하는 질문

### Q1. JSON을 직접 고치면 안 되나요?

**안 됩니다.** `데이터/json/`은 엑셀에서 자동 생성되는 결과물이라, 다음 빌드 때 덮어써집니다. **`LUNA_System.xlsx`(제조·운영) 또는 `LUNA_Narrative.xlsx`(대사·서사)를 고치고 `build.py`를 돌리세요.**

### Q2. 새 칵테일을 추가하려면?

1. `Cocktails` 시트에 행 추가 (id·이름·가격·도수·잔·mix·태그…)
2. `RecipeLines` 시트에 재료 줄 추가
3. `time_limit`·`scoring_items`는 적지 마세요 — 자동 계산됩니다
4. `tier`·`unlock_day`는 **비워두면 자동**, 직접 정하고 싶으면 `tier_override`·`unlock_day_override`에 적으세요
5. 필요한 재료가 `ShelfItems`에 없으면 먼저 추가(`kind: ingredient`)
5. `build.py` 실행

### Q3. 특정 손님이 특정 술을 좋아하게 하려면?

`Tastes` 시트에 한 줄 추가하면 됩니다.

```
character_id: port,  seq: 1,  when: cocktail.id == gin_fizz,  tier: love
```

**`seq` 순서가 중요합니다.** 구체적인 조건(특정 칵테일)을 위에, 넓은 조건(태그·도수)을 아래에 두세요. 위에 넓은 조건이 있으면 아래 구체적인 조건이 영영 안 걸립니다.

### Q4. "또는(OR)"을 쓰고 싶은데요?

**줄을 두 개로 나누세요.** 이건 제약이 아니라 설계 결정입니다.

```
❌  when: cocktail.abv >= 20 || cocktail.tag(독한)
✅  줄 1 → when: cocktail.abv >= 20
    줄 2 → when: cocktail.tag(독한)
```

### Q5. 대사에 영어를 아직 못 넣었는데요?

**빌드가 실패합니다.** 임시로라도 넣어야 해요. 나중에 몰아서 번역하다가 빠뜨리는 사고를 막기 위한 규칙입니다.

### Q6. `unlock_day: 99`는 무슨 뜻인가요?

**"날짜로는 절대 안 풀린다"** 는 뜻입니다. 게임이 13일차까지라 99일차는 영원히 안 오죠. 그래서 **퀘스트로만 풀리는 재료·레시피**에 이 값을 씁니다. 실제 해금은 `unlock_when` 조건이 담당합니다.

### Q7. 데이터를 고쳤는데 게임에 반영이 안 돼요.

`bundle_proto.py`를 안 돌렸을 가능성이 큽니다. **두 단계 모두** 실행해야 해요.

```bash
python3 데이터/tools/build.py          # 엑셀 → JSON
python3 데이터/tools/bundle_proto.py   # JSON → 웹 프로토 data.js
```

### Q8. `gen_luna_data.py`는 뭔가요? 돌려도 되나요?

**절대 돌리지 마세요.** 그건 최초에 코드로 시트를 만들어낸 스크립트라, 실행하면 **엑셀이 통째로 덮어써집니다.** 팀이 저작을 시작한 지금은 봉인된 파일입니다.

# H. 요약 카드

```
┌─────────────────────────────────────────────────────────┐
│  작업 흐름                                               │
│    System.xlsx + Narrative.xlsx → build.py → json/      │
│                                 → bundle_proto.py       │
│    ⚠ json/은 결과물. 손대지 말 것                        │
├─────────────────────────────────────────────────────────┤
│  공통 규칙 4가지                                         │
│    ① 모든 표시 텍스트는 {ko, en} 필수                    │
│    ② 계산 가능한 값은 자동 (tier·해금일·제한시간)         │
│    ③ null = 해당없음 / "" = 조건없음(항상 참)             │
│    ④ when(조건) · effects(효과)는 전 파일 공용 · OR 없음  │
├─────────────────────────────────────────────────────────┤
│  파일 그룹                                               │
│    A 마스터 10  게임의 사전 (칵테일·선반·캐릭터·취향…)    │
│    B 밸런스  1  숫자 튜닝 전부                            │
│    C 스케줄  4  하루 진행 (일차·손님·위치·지점)           │
│    D 서사    3  퀘스트·엔딩·분기주문                      │
│    E 대본    4  씬-스텝-선택지                            │
├─────────────────────────────────────────────────────────┤
│  꼭 기억할 개념 3개                                       │
│    · 해금의 주체는 재료 (칵테일 해금일은 파생 or 수동)     │
│    · recipe는 실행순서가 아니라 채점 정답표                │
│    · 선반 4단계(잔→도구→가니시→재료) 후 제조 시작          │
│    · 취향은 first-match — 상황(플래그)이 취향을 뒤집는다   │
└─────────────────────────────────────────────────────────┘
```
