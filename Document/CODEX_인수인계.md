# Project L.U.N.A — Codex 인수인계

기준일: 2026-08-22  
작업 범위: `Human-Bartender/Document/`

이 문서는 다음 작업자가 현재 데이터·기획 상태와 정본 문서를 빠르게 찾을 수 있도록 만든 최신 인수인계다. 기존 [LUNA_인수인계.md](./이준서/마크다운/LUNA_인수인계.md)는 2026-08-01 기준의 과거 기록으로, 현재 시트 수·스키마·일차 체계·제조 규칙과 다른 내용이 많다. 현재 작업에서는 이 문서와 [CLAUDE.md](./CLAUDE.md)를 먼저 읽는다.

## 1. 가장 먼저 알아야 할 것

- 실제 작업 대상은 `Document/`뿐이다. Unity 엔진 `HumanBartender/`, 아트 `ArtResources/`, 리포지토리 루트 설정 파일은 수정하지 않는다.
- 데모는 **Day 0·1·2·3, 총 4일**이다. 내부 데이터와 화면 표시는 모두 0부터 시작한다.
- 현재 데이터 계약은 **schema 2.5.0**, 배포 번들 계약은 **1.0.0**이다.
- 저작 원본은 [LUNA_System.xlsx](./데이터/LUNA_System.xlsx)와 [LUNA_Narrative.xlsx](./데이터/LUNA_Narrative.xlsx)다.
- `Document/데이터/json/`은 빌드 산출물이다. JSON을 직접 수정하지 않는다.
- `gen_luna_data.py`는 엑셀 원본을 덮어쓸 수 있으므로 실행하지 않는다.
- 현재 우선순위는 **0일차를 완성하고 빌드를 뽑는 것**이다. Day 3 종료 방식과 후속 콘텐츠는 지금 임의로 확장하지 않는다.
- 2026-08-19 기준 엄격 빌드는 통과한다. 0일차 구현을 막는 데이터·기획 결정은 없다.

### 정본의 우선순위

1. 엑셀 원본: 기획자가 수정할 데이터의 정본
2. 같은 빌드에서 생성된 JSON: 프로그래머가 실제로 읽는 데이터 계약
3. 최신 노션 시스템·데이터 문서: 흐름, 책임, 예외, 구현 설명
4. 이 문서와 `CLAUDE.md`: 작업자가 빠르게 상태를 파악하기 위한 요약
5. 과거 변경 문서와 프로토타입: 결정 근거와 화면 참고

문서와 실제 데이터가 다르면 같은 빌드에서 생성된 JSON을 우선 확인하고, 원인은 엑셀과 문서 양쪽에서 바로잡는다.

### 호환성 유지형 필드와 배포 목록

- 신규 구현은 `cocktails.json → target_mix_method`, `target_prep_action`, `tags[].id`를 우선 사용한다.
- 기존 `mix`, `prep`, `tags[].ko`는 현재 로더와 대본을 깨지 않기 위해 한 버전 유지한다. 신규 필드와 값이 다르면 임의 보정하지 않고 데이터 오류로 처리한다.

- `manifest.json → files`의 파일별 SHA-256·바이트 수와 `bundle_sha256`으로 부분 교체와 QA 혼입을 검사한다.
- `hound`는 `characters.json`에 등록된 컷씬 전용 인물이다. `field_anims.json`의 예외 문자열로 처리하지 않는다.

## 3. 0일차 구현 기준

### 플레이 흐름

```text
메인 타이틀
→ 연구소 인트로 컷신
→ 출근길
→ 바 최초 진입
→ 개점 대화·튜토리얼
→ 1부 검사
→ 0일차는 랜덤 손님이 없으므로 2부로 전환
→ 포트 주문·제조·서빙
→ 2부 종료
→ 일일 매출 정산
→ 퇴근길
→ 집
→ 잠들기
→ 0일차 종료
```

### 0일차 칵테일과 재료

- 메뉴에 보이는 칵테일은 **진토닉**과 **진피즈**뿐이다.
- 크리스 튜토리얼 주문은 진토닉이다.
- 포트 주문은 진피즈다.
- 플레이어가 수동으로 선택하는 재료는 **진**과 **탄산수**뿐이다.
- 토닉워터와 소다수는 `soda_water` 하나로 통합했다.
- 화면 표시명은 한국어 `탄산수`, 영어 `Carbonated Water`다.
- 진피즈의 레몬과 설탕은 자동 적용·비채점이다.
- 0일차에는 일반 랜덤 손님이 등장하지 않지만, 1부 일반 손님 시스템 자체는 이후 일차를 위해 구현돼 있어야 한다.

### 저장 정책

- 수동 저장은 집에서만 가능하다.
- 수동 저장 슬롯은 5개다.
- 자동 저장 슬롯은 1개이며 새 저장이 발생할 때 덮어쓴다.
- 자동 저장은 다음 네 지점에서만 실행한다.
  1. 집을 나서 출근길에 진입한 직후
  2. 바에 처음 들어온 직후
  3. 2부를 시작하기 직전
  4. 2부 종료 후 일일 매출 정산 커밋이 완료된 직후
- 1부 도중 종료하면 바 최초 진입부터 다시 진행한다.
- 2부 도중 종료하면 2부 첫 장면부터 다시 진행한다.
- 제조·기믹·대사·손님 단위의 중간 상태는 저장하지 않는다.
- 출근길 복구 위치는 `home_door`, 퇴근길 복구 위치는 `bar_door`다.
- 외부 거리의 세부 좌표와 개별 상호작용 중간 상태는 저장하지 않는다.
- 집 수동 저장은 `world.location_id = home`, `world.spot_id = home_spawn_entry`와 함께
  `world.home_context = day_start | pre_work_return | after_work`를 기록한다.
- 집의 수동 저장·취침 조건은 대상 하나에 고정하지 않고 `HomeInteractable.actions[]`의 행동별 입력과
  `available_contexts[]`로 구분한다. 이 구조는 구현 계약이며 정적 Config에 중복 저장하지 않는다.
- 집 핵심 기능용 UI 문구 7종은 `LUNA_Narrative.xlsx → UIStrings`와 `ui_strings.json`에 ko/en으로 반영됐다.
  자동 저장 실패는 이전 자동 저장을 보존하고 비차단 안내 후 현재 구간을 계속 진행한다.

## 4. 바 운영과 제조의 핵심 계약

### 주문·제조·서빙

- `Order Cocktail`은 손님의 주문에 속한다.
- `Selected Cocktail`과 `Actual Craft`는 손님과 연결되지 않은 `CraftAttempt`에 속한다.
- 1부에서는 완성 잔을 유효한 코스터에 드롭할 때 `CraftAttempt`와 `target_order_id`가 처음 연결된다.
- 2부에서는 파트 컨트롤러가 현재 주문 문맥을 보유하지만, 공용 제조 엔진은 손님 ID나 주문 ID 없이 제조 결과만 반환한다.
- 제조 단계에서는 `craft_score`와 `craft_grade`까지만 결정한다.
- 서빙 단계에서 주문 일치, 핵심 재료 누락, 최종 Sewage 여부와 `final_grade`를 확정한다.
- 2부 대본의 기본 세트는 `order → craft → serve`다.
- `order.text`가 있으면 주문자의 대사로 화면에 먼저 출력한다.
- `serve.actor`는 직전 `order.actor`와 일치해야 한다.

### 기믹·판정

- 실제 기믹 큐는 플레이어가 고른 재료와 도구로 만든다.
- 따르기·필업의 액체 색은 `shelf_items.json → color`, 투명도는 `liquid_alpha`를 사용한다. `liquid_alpha`는 0.0~1.0이며 pour/fill_up 재료에만 존재한다.
- 정답 레시피는 목표값과 채점 기준으로만 사용하며 오선택을 정답으로 자동 보정하지 않는다.
- 셰이킹은 성공+실패 합 20스택에서 자동 종료한다.
- 스터는 성공+실패 합 10스택에서 자동 종료한다.
- 스퀴즈·설탕·얼음은 데모에서 자동 적용·비채점이다.
- Fill-up은 Pour 종류에 포함하며 `weight_pour`를 공유한다.
- 최종 제조 점수는 같은 기믹 종류의 평균을 대표 점수로 만든 뒤, 실제 등장한 기믹의 가중치를 정규화해 계산한다.
- 주문 불일치와 핵심 재료 누락의 강제 Sewage는 서빙 시점에 적용한다.

### 일반 손님

- 공란 주문은 해당 일차에 해금된 `status=confirmed` 칵테일 중 매 회차 동일 확률로 독립 추첨한다.
- 같은 손님이 같은 칵테일을 연속 주문할 수 있다.
- 고정 `order`가 있는 슬롯은 무작위 추첨을 사용하지 않는다.
- 유효 코스터 드롭과 서빙 인내심 종료가 같은 프레임이면 timeout을 우선한다.
- timeout이면 손님이 퇴장하고 드롭은 서빙으로 커밋하지 않는다.
- 손님의 정상·시간 초과 퇴장 연출이 끝나면 해당 좌석의 코스터와 좌석에 귀속된 잔을 제거한다.
- 추가 주문이 이어질 때는 손님과 코스터를 유지하고 이전 회차의 빈 잔만 제거한다.
- 일반 손님 표정·애니메이션 데이터는 유지하지만 현재 리소스가 없으면 기본 정지 스프라이트 한 장으로 표시한다.
- 여성 외형은 남성과 같은 피벗·레이어 기준을 사용한다. 정확한 캔버스 크기는 리소스가 나온 뒤 확인한다.

### DATA_ERROR

- DATA_ERROR는 플레이 실패가 아니라 데이터·Config·참조 오류다.
- 첫 오류에서는 `다시 시도`와 `제조 취소`를 한·영으로 제공한다.
- 다시 시도는 같은 Actual Craft로 기믹 큐를 다시 만들고 새 `request_id`를 사용한다.
- 제조 취소는 CraftAttempt를 폐기하되 손님의 대기 주문은 유지한다.
- 같은 CraftAttempt에서 같은 오류가 2회 연속 발생하면 안전 이탈을 우선 안내한다.
- 오류 상태·점수·등급·정산 결과는 저장하지 않는다.
- 안전 이탈 후에는 가장 최근의 고정 전환점 자동 저장으로 돌아간다.

## 7. 데이터 작업 절차

1. `Human-Bartender`에서 `git status --short -- Document`로 기존 변경을 확인한다.
2. 다른 사람의 미커밋 변경과 겹치는지 먼저 확인한다.
3. 엑셀 원본만 수정한다.
4. 새 규칙에 검증이 필요하면 `build.py`에 검증을 추가한다.
5. 고의로 잘못된 값을 넣은 임시 복사본에서 검증이 실제로 실패하는지 확인한다.
6. 원본에서 `build.py --strict`를 실행한다.
7. 생성 JSON의 키·타입·참조·한영 문자열과 `manifest.json`의 파일 해시를 확인한다.
8. 엑셀 수정은 변경 범위를 렌더링해 글자 잘림과 서식 파손을 확인한다.
9. 스키마가 바뀌면 데이터 구조 문서와 당일 데이터 변경 사항을 함께 수정한다.
10. 노션은 `update_content`로 필요한 절만 바꾸고, 수정 후 반드시 다시 fetch해 확인한다.

## 10. 이번 인수인계 작성 직전 반영된 내용

- 저장 정책을 schema 2.5.0에 반영했다.
- 집 전용 수동 저장 5칸과 고정 자동 저장 1칸을 Config로 만들었다.
- 자동 저장 지점 네 곳과 외부 복구 앵커 두 곳을 데이터로 만들었다.
- 저장 관련 한·영 UI 문자열 5개를 추가했다.
- 집 출입·취침·덮어쓰기·저장 완료·자동 저장 실패·맵 전환 실패용 한·영 UI 문자열 7개를 추가해 UIStrings를 59키로 갱신했다.
- 집 기능 UI 7키의 존재와 ko/en 공란 검증을 추가했고, 고의 누락 테스트와 정상 엄격 빌드를 모두 통과했다.
- 비정상 종료 문구를 “마지막 자동 저장에서 다시 시작”한다는 의미로 한·영 수정했다.
- 1부·2부·제조의 중간 상태는 파일에 저장하지 않는 것으로 문서 충돌을 정리했다.
- 저장 시스템, 데이터 구조, 1부·2부 문서, 데이터 변경 사항, 기획서 수정 내용을 같은 기준으로 최신화했다.
- 엄격 빌드와 스프레드시트 오류 검사를 통과했다.
- Tags 시트에 언어 독립 `tag_id` 16개를 추가하고 `cocktails.json → tags[].id`로 출력한다.
- 칵테일 정답에 `target_mix_method`·`target_prep_action`을 추가했으며 기존 `mix`·`prep`은 호환용으로 유지한다.
- `hound`를 컷씬 전용 Characters 행으로 등록해 FieldAnims 참조를 정상화했다.
- Tags ID·FieldAnims 캐릭터·병 개봉 정답 검증을 추가했다. 상점 교차 검증 코드는 예약 상태지만 데모에는 상점 데이터가 없다.
- `manifest.json`은 운영 31파일과 Day 99 QA 3파일을 분리하고 파일별 SHA-256과 번들 해시를 기록한다. Day 99 거리도 단일 `qa/interact_points_day99.json`을 사용하며 `field_entities_day99.json`은 폐기했다.
- 완·노점·상점 데이터를 데모 거리 데이터에서 제거했다. 삼호·시바 첫 만남과 삼호 사망·생존 결과는 거리 대본에서 제외하고 `Cutscenes`의 별도 연출 리소스로 유지한다.
- 거리 NPC는 E 상호작용으로만 대사를 시작한다. 고양이 지점은 `actor=bubi`인 전신 캐릭터로 표시하며 E 상호작용 후 `d3_alley_cat`을 실행한다.
- 현재 운영 거리 데이터는 `Spots` 7개 앵커, `InteractPoints` 7행, `script/street.json` 8씬이다. 같은 `spots.json`에는 Day 99 QA 앵커 7개가 추가되어 총 14행이다.
- 거리 대화 선택 정보는 `interact_points.json → dialogue_flows[]`가 소유한다. 각 항목은 `scene_id`·`day`·`flow_seq`·`play_type(once|repeat)`·`when`으로 구성되며, 일반 순차 진행은 play_type으로 처리하고 when은 특수 조건에만 사용한다.
- `script/street.json`과 `script/qa/street_day99.json`은 씬의 `id`와 `steps`만 배포한다. 상태 변경은 `set_state` 스텝, 선택지는 해당 choice 스텝의 `options[]`, 선택 결과는 `result_steps[]`의 `set_state`·`goto`로 표현한다. 거리 씬의 구 `on_complete_effects`와 루트 `choices`는 더 이상 배포하지 않는다.
